# YADECK の deck を書く

YADECK は data(YAML)が「何を伝えるか」だけを持ち、見た目は view(React の Layout)が決めるスライドジェネレータ。
このスキルは次の 5 ステップで進める。各ステップの結果を利用者に短く報告し、ステップ 4 は利用者の合意を得てから 5 に進む。

## ステップ 1: YADECK の deck リポジトリか確認する

次の 2 つが揃っていれば deck リポジトリ。揃っていなければ、その旨を伝えて止まる(ツール側リポジトリ `packages/slide-*` を直す話なら別の作業)。

- `slide.config.ts` があり、`@yadeck/slide-core` の `defineConfig` を使っている
- `package.json` の dependencies に `@yadeck/slide-core` がある

あわせて `slide.config.ts` の `decks`(既定 `decks`)、`publicDir`(既定 `public`)、`plugins` を読む。`plugins` に自作プラグイン(`src/`)があれば、そこで bind している tags も使える。

## ステップ 2: schema を確認する

使える tags とフィールドは `.slide/deck.schema.json` が正。無い、または `slide.config.ts` / `src/` / ツール側より古いときは生成する。

```sh
npm run schema      # = npx yadeck schema。.slide/deck.schema.json を生成する
```

schema の読み方:

- `$defs.slide.anyOf` / `$defs.block.anyOf` の各要素が Layout の候補。`description` が「tags: xxx — 用途」の形で、`properties` がそのフィールド(`$tags` `$items` `$text` は構造キー)、`required` が必須
- `description` が「tags なし(既定)」の要素が fallback。slide の tags に該当する Layout が無いとこれになる
- 単一キー形式(`maxProperties: 1` の要素)の `properties` のキーが、YAML でそのまま書ける tags の組み合わせ

tags は見せ方のヒント。候補に無い tags を書いても fallback で描画はされるが、意図した見せ方にはならない。欲しい見せ方が無ければ、data を曲げずに「Layout が無い」と報告する(ツール側か `src/` のプラグインで足す)。

## ステップ 3: 対象ファイルと位置を確認する

- `decks/` の YAML を列挙し、どの deck に書くかを決める。1 つしか無ければそれ、複数あれば利用者に聞く
- 既存の内容を読み、どの位置に追加するか(末尾か、既存スライドの置き換えか)を確認する
- 渡された入力(原稿、メモ、イメージの指示、既存スライドの画像や PDF)を読む。原稿なら該当する見出し・段落を特定する
- `public/` にある画像などの素材も確認する

## ステップ 4: スライドに記載する内容を提案する

1 ページずつ、YAML を書く前に why → how → what の順で決め、合意を取ってから書く。運用のこと(ページ数の区切り、案の数)は利用者に聞かず、この節の通りに進める。

### まず入力の形を見極める

利用者が何を渡してきたかで進め方が変わる。判別できなければ、どれかを一言で聞く。

| 入力 | 進め方 |
|---|---|
| **原稿がある**(話す原稿、箇条書きのメモ、既存の文書) | 原稿の該当範囲から why を読み取り、下の順で組み立てる |
| **何も無く、相談しながら決める** | why から順に、候補を添えて利用者に聞きながら組み立てる。`note` には決めた要点だけを入れ、話す文を創作しない |
| **明確なイメージが渡される**(文章での指示、手書きやテキストのスケッチ) | why / how を導き直さない。書かれた内容をそのまま data に写し、指示された見せ方(「3 つ横に並べて」など)は schema の description から合う tags に対応付ける。合う Layout が無ければ、data を曲げず「その見せ方の Layout は無い」と言う |
| **既存のスライドが渡される**(画像、PDF、他ツールの出力) | 1 ページずつ読み取り、見出し・本文・コード・図などを 1:1 で data に写す。内容を要約・改善しない(頼まれたときだけ下の順で見直す)。スピーカーノートがあれば `note` へ。図や写真は素材として必要なので `不足:` に書く |

### 組み立ての順(why → how → what)

what(載せる情報)から考えない。何を伝えたいかが先で、次に構成の類型を選び、最後に類型の枠に中身を埋める。

1. **why: このページで聴衆に何を伝えたいか。そして聴衆は何を知っている前提か。**
   ページは「聴衆が既に知っていること(前提)」と「伝えたいこと(結論)」の間を埋めるためにある。結論だけ決めても中身は決まらない。前提の想定が違えば、同じ結論でも載せるものが変わる。
   - 伝えたいこと: 話の流れの中でこのページがある理由を 1 文にする。前のページから何を受けて、次のページに何を渡すか。これが見出し(主張)になる。話題名ではなく、聴衆が持ち帰る 1 文。表紙・章扉のような構造上のページだけは役割(タイトル / 章名)が見出しになる
   - 前提: このページを見る時点で聴衆が知っていること、思い込んでいること。前のページまでで示したこと、一般的な知識、原稿が「〜のはず」「普段は〜」と書いている箇所から読み取る
   - 埋めるもの: 前提から結論までの道筋。ここが what の骨格になる(例: 前提「スライドは原稿を縮めたもの」→ 縮めても文字は多い → 聴衆は読むか聞くかの片方しかできない → [文字で埋まったページそのもの] → 結論「1 ページで伝えるのは 1 つ」)
   原稿があれば該当範囲と前後のページを見て読み取る。why が 2 つあるならページを分ける。
2. **how: 構成の類型を選ぶ。** ページの構成は「配置 × 主役」で指定する(主役が図解なら下位パターンまで)。候補を 2〜3 出して選んでもらう。
   選ぶ基準は「1 ページ 1 点」。焦点(最初に見るもの)が 1 つに定まり、残りが小さく添えられる構成にする。同じ重さの情報を並べるだけの構成は避ける。
3. **what: 類型の枠に中身を埋める。** ページの中を 1 つの論理構成として組む。
   - 前提の再確認: 説明側(箇条書きなど)は、why で決めた道筋を前提から順に辿る語句にする。結論と無関係な事実を並べない
   - 焦点: 道筋の最後の段は主役(現物や図)が示す。文字で繰り返さない(「文字が多い」と書かず、文字で埋まったページそのものを見せる)。主役の中で「ここを見る」箇所を 1 つ決め、data の `focus` で指定する(`code` なら行、`list` なら項目。図は描く段階で焦点を入れる)。焦点が無い主役は飾りになる
   - 結論: 見出し
   類型が求めるもの以外は入れない。文字は要素に付く語句やラベルまでで、文は見出しと description だけ。
   ほとんどのページには、見出しの下に 1 行の `description`(このページが何を示すか)を付ける。表紙・章扉・一言のページには付けない。
   原稿に無い材料(数値、名前、画像)は補わない。要るなら `不足:` に書いて聞く。
4. **検査。** 書き終えたら次を確認する(書く手順ではなく検査)。
   - 3 秒見て目をそらし、何のページか言えるか(言えなければ要素を減らすか分ける)
   - 口で言えば済むもの(理由づけ、つなぎ、感想、例え話、小ネタ)が混ざっていないか。混ざっていれば `note` へ
   - 原稿の文を縮めて並べただけになっていないか

`note` には原稿の該当範囲をそのまま入れる。既存ページの編集は、変更する範囲にだけ上の順を当て、変更前後を並べて示す。

### 構成の類型

#### 主役(ページで一番大きく見せるもの)

| 主役 | 内容 | basic の block |
|---|---|---|
| 一言 | 1 文だけ | 本文 1 行(tags 無し) |
| 現物 | コード、ログ、画面、写真 | `code` / `image` |
| 図解 | 下記の下位パターン | 流れは `flow`、他は `image`(SVG を描く) |
| 数字 | 1 つの数と単位 | `stat` |
| 列挙 | 並列の項目 3 つまで、各項目に一言 | `item` / `list` |
| 手順 | 順序のある段階、各段階に一言 | `flow`(縦: STEP ピル + レール + 点線、横 `direction: row`: 吹き出し番号の枠カード)、`flow boxed`(角丸の枠を ▽ でつなぐ)、`flow framed`(全体を 1 つの枠で囲む)、`flow grid`(矢印形の枠を 2 列。段数が多いとき) |
| 引用 | 引用文と出典 | `quote` |

#### 図解の下位パターン

| パターン | 形 | 例 |
|---|---|---|
| 流れ | 箱と矢印の連なり(`flow` block で描ける) | 処理の流れ、変換の段階 |
| 構造 | 箱の入れ子、層、ツリー | アーキテクチャ、階層 |
| 関係 | ノードと線 | 依存関係、相関 |
| 時系列 | 時間軸に出来事 | 経緯、タイムライン |
| 場面 | 登場するものをアイコンで配置 | 聴衆の中で 1 人だけ前を向いている |
| 表 | 行と列のマトリクス | 機能 × 対応状況 |
| グラフ | 量の比較や推移 | 棒、折れ線 |

#### 配置(主役をどう置くか)

| 配置 | 形 | 使いどころ | basic の tags |
|---|---|---|---|
| 単独 | 主役だけ。キャプション 1 行まで | 現物や一言を見せ切る | tags 無し |
| 全面＋一言 | 写真や図を全面に敷き、短い一言を重ねる | 場面、印象づけ | (Layout 無し) |
| 説明＋主役 | 語句数行と主役を左右に | プロフィール、コード解説 | tags 無し(2 pane) / `profile` |
| 主役＋キャプション | 主役を上、説明を下に(または逆) | 図解の読み方を添える | tags 無し |
| 主役＋注釈 | 主役の中の箇所に吹き出しや印で注釈 | コードの該当行、画面の該当箇所 | (Layout 無し。SVG に描き込む) |
| 対比 | 主役を 2 つ横に並べ、違う箇所を焦点に | 期待と実際、before / after | `two-column` |
| 分割 | 3〜4 を等分に並べる | 選択肢、サービス一覧 | `card` / `columns` |
| 全体＋拡大 | 全体を小さく、注目部分を大きく | ログの 1 行、図の一部 | (Layout 無し。SVG に描き込む) |
| 主＋従 | 主役を大きく、補助の現物や数字を小さく添える | 図＋根拠の数字 | tags 無し(2 pane) |
| 段階開示 | 同じ構成を複数ページで少しずつ増やす | 流れを 1 段ずつ | ページを複数書く |

- 表紙は「単独 × 一言」(basic では `header`)、章扉も「単独 × 一言」(`section-header`)、まとめは「単独 × 列挙」、プロフィールは「説明＋主役 × 現物(写真)」
- 「Layout 無し」の配置は、現状の basic では SVG に描き込むか、`src/` のプラグインで Layout を足す。data を曲げて近い見た目にしない
- 図解の SVG は `public/` に書いて `image` で置く。1280x720 の pane に収まる比率で、テーマの色(primary / accent / ink / muted)を使い、文字は要素のラベルだけにする
- 頻度や割合が焦点のときは、個数で描くと比率に誤読される(10 回の発表のうち 1 回を赤くすると「10 回に 1 回」に見える。「たまに」を伝えたいなら回数を固定して描かない)。繰り返しを並べ、その中の 1 つとして描く。構成の単位(1 回の発表で 3 ページなど)も残したいなら、組を縦に積んで「…」で省略し、最後の組にだけ違いを置く
- 「説明＋主役」では、左から右へ視線を流す要素(矢印、番号、色のつながり)を主役の左端に置く

### 利用者への聞き方

why → how(類型) → what の順に、1 つずつ聞く。前の答えを反映してから次を出す。why は「伝えたいこと」と「聴衆の前提」をひと組で聞く(候補ごとに前提の想定を添える)。how は「配置 × 主役」の候補を 2〜3 並べ、それぞれ何が焦点になるかを一言添える。

- **候補を添える。** 各問に推奨を先頭にした候補を出す(最大 3 つ)。利用者にとっては訂正を書くより候補から選ぶほうが楽なので、迷った箇所は候補を出す。理由は書かない
- **ホストに選択 UI があればそれを使う。** Claude Code なら AskUserQuestion で 1 問ずつ、候補を選択肢にする。what の候補は要約ではなく、画面に出る文面そのものを見せる(選択肢の preview にページの文面全体を書く)。UI の無いホストではテキストで候補を並べる
- **質問文に内部の言葉を使わない。** 「主張」「材料」「block」「what」ではなく、「このページで伝えたいこと」「どう見せるか」「画面に出す文面」のように聞く
- **利用者の返事は「選ぶ」でも「直接指示する」でもよい。** 直接指示はそのまま採る。指示がこの節の規則に反していても言い直さず、従う。指示で埋まらない残りだけ推奨で埋める
- OK → ステップ 5。NG だけで具体が無い → why / how / what のどこが違うかを一言で聞く
- 「任せる」と言われたら以降は質問を挟まず 5 まで進め、最後に全ページを一覧で見せる

### 提案の形(UI の無いホスト向け、または最終確認用)

```
### ページ N(位置): <見出し = 伝えたいこと 1 文>   [tags: <1 つ、無ければ省く>]
前提: <聴衆が知っていること> → <道筋> → <結論>
description: <見出しの下の 1 行>
構成: <配置 × 主役>   焦点: <主役の中のどこ>
画面:
  - <block>: <内容 1 行>
  - <block>: <内容 1 行>
note: 原稿「<冒頭数語>」〜「<末尾数語>」(行番号や見出し)   # 原稿が無ければ入れる要点
不足: <手元に無く要るもの(画像、数値など)>                  # 無ければ行ごと省く
```

## ステップ 5: 書き込んで確認する

1. YAML を書く(書き方は下記)。`note` には原稿の該当箇所をそのまま入れる
2. `npx yadeck validate` でフィールドの誤りが無いことを確認する
3. `npx yadeck check --deck <deck> --slide <N> --png` で、そのページを Chromium で描画して検査する(N は `#s<N>` の数字)
   - `error`(スライドの外へのはみ出し、枠で切れて見えない文字)は、利用者に見せる前に直す。data で直せなければ Layout の問題として報告する
   - `warn`(端の余白への食い込み、コードが下限サイズまで縮んでいる、コードの折り返し)は、見せ方の問題として報告に添える
   - 見た目を目で確かめたいときは、書き出された PNG(`dist/png/<deck>/s09.png`)を読む。全ページを見るなら `npx yadeck png --deck <deck>`。ブラウザ操作のツールでの確認はしない
   - playwright が無いと言われたら、`npm i -D playwright && npx playwright install chromium` を利用者に提案する
4. 利用者に書いた YAML を見せ、ステップ 4 の提案から変えた点があれば言う。見せ方の問題は view 側の話なので分けて報告する

### YAML の書き方(sugar)

```yaml
# yaml-language-server: $schema=../.slide/deck.schema.json
- header: { title: 発表タイトル, subtitle: 副題, author: 名前, affiliation: 所属, event: イベント名 }
- - heading: 見出し            # tags 無しの slide。配列の各要素が block
  - 文字列は tags 無しの block(= 本文 1 行)
  - body: "**markdown** と `code` が使える"
  - list: |                    # 行ごとに 1 項目
      項目 1
      項目 2
  - code: { lang: java, $text: "..." }
  - image: { src: ./x.png, $text: キャプション }
  - note: 話す内容。画面にも印刷にも出ない
- card:                        # slide の tags は単一キーで書く。値が配列なら items
  - heading: 見出し
  - item: { title: 名前, $text: 説明 }
- description: 見出しの下に添える 1 行   # slide のフィールドを書くときは map にして $items を使う
  $items:
    - heading: 見出し
    - 本文
- card:
    description: tags とフィールドを両方書くときはこの形
    $items:
      - heading: 見出し
```

- 単一キーの map `{ K: V }` は `K` を空白区切りで tags にする(`section-header t` のように複数可)
- 構造キー(`$tags` `$items` `$text` `$meta` `$version`)はフル記述のときだけ `$` 付きで書く
- `public/` に置いたファイルは `./name.ext` で参照する
- tags 無し slide の自動レイアウト: テキスト系は全部で 1 pane、`code` / `image` / `video` / `flow` は 1 つずつ 1 pane。1: 全面、2: 左右、3: ト型、4: 十字、5 以上: 左右 2 列。詳細は schema の「tags なし(既定)」の description

## やってはいけないこと

- what(載せる情報)から考え始める。why → how → what の順を守る
- 原稿の文をそのまま、あるいは少し縮めて箇条書きにする
- 伝えたいこと(why)が無いページ(話題名だけの見出しに情報を並べたページ)を作る
- 聴衆の前提を考えずに結論だけ置く。前提から結論への道筋が無いページは「だから何？」になる
- 渡された入力に無い数値・名前・文を補う
- 見た目のための tags やフィールドを data に増やす
- schema に無い tags やフィールドを使う(validate で落ちる)
- ステップ 4 の合意を取らずに書き込む、確認せずに次のページへ進む
